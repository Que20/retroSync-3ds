# V1 behavior and recovery

V1 installs single-file GBA ROMs and ZIP archives containing exactly one GBA ROM. Other platforms remain browsable.
Archives are size-bounded, checked for path traversal, encryption and symlinks, streamed through zlib, and checked
against the member CRC. Downloaded files are checked against the advertised size and available MD5, then the GBA
header/size is validated. Files are staged on the same SD volume. Existing untracked destinations are never overwritten.

## Login and account isolation

Settings uses RomM's OAuth password grant at `/api/token`, then rotating refresh tokens. No password is retained.
Requested scopes: `me.read platforms.read roms.read assets.read assets.write devices.read devices.write`.
Normal RomM local accounts are supported; browser-only OIDC/SSO is not implemented. HTTPS is the default.
Advanced HTTP opt-in exposes credentials and should only be used on a trusted test LAN.

The server's `/api/users/me` identity and configured base URL scope the install records. Changing account does not
reuse another account's save baseline. Session credentials live in `/3ds/RetroSync3DS/settings.ini` and its recovery
backup; signing out removes these copies. SD access is possession-based, not a secure credential vault.

## Save mapping and compatibility

Open_agb_firm's global `useSavesFolder`, global/per-game `saveSlot`, and explicit `saveType` overrides are read.
The app does not rewrite emulator configuration. If the slot/path or an incompatible chip override changes,
synchronization stops until the link is reviewed. An unknown chip type requires explicit user verification.

Supported battery lengths: SRAM 32 KiB; FLASH 64/128 KiB; EEPROM 512 bytes/8 KiB. The user explicitly identifies the
remote representation: raw emulator battery data or open_agb_firm. EEPROM conversion reverses each eight-byte
block. This is not a generic save-container converter: compressed save containers, unknown formats and save states
are rejected. ROM signature detection is a hint for SRAM/FLASH, never proof of EEPROM size or hacked-game behavior.

New links default to the mGBA/raw representation used for GBA by RomM/EmulatorJS; the user can explicitly choose
open_agb_firm representation instead. A link targets an exact nonempty named RomM slot and producer. Archival null slots and empty-string slots remain
history; they are not silently treated as `autosave`. A producer change requires review. For RomM 5.4.0 the current
slot row is selected by `(updated_at, id)` descending, matching the server's guarded upload order, including tied
timestamps. A null server hash prevents automatic writes.

## Conflict and concurrency behavior

Each successful sync stores the local and server hashes. Decisions use a canonical local representation and a
three-way baseline, not timestamps. Both changed means **Keep local / Keep remote / Cancel**, defaulting to Cancel.
Copies downloaded from RomM are retained under the account directory before conflict resolution. Local replacements
keep a `.rs-backup-<SHA256>` copy next to the save.

Uploads use the registered device and `overwrite=false&autocleanup=false`; they append history. Before upload the
client verifies/downloads the current remote copy, acknowledges that exact version, then lets RomM's guard reject a
concurrent change with HTTP 409. It never uses forced overwrite. Downloads use `optimistic=false`; acknowledgement
happens only after checked bytes have been installed locally. This is per-game asset/device synchronization; the
server's negotiate/session-completion protocol is not used.

If an upload loses its response, the manifest records `upload-unconfirmed`. A later attempt searches history for
that exact hash. With no evidence, it stops instead of blindly resending. Check the slot in RomM before manually
repairing that state. Do not delete tracking files merely to dismiss an unknown upload outcome.

Missing tracked local or remote saves do not trigger deletion or an automatic recreation. Review the files and
explicitly relink when restoring is intended. Verify installed ROM hashes again if the game was replaced externally.

## Power loss and backups

Install/save records are stored in `/3ds/RetroSync3DS/accounts/<server-and-user-hash>/` with versioned JSON and prior
metadata backups. Replacement journals and verified backups allow recovery from interrupted file renames, including
libctru's overwrite semantics. Ambiguous recovery preserves evidence and asks for review. The app never promises
atomic FAT writes or secure erasure of SD storage.

Backups and immutable downloaded save originals are retained rather than automatically pruned. Watch free SD space;
copy backups to a computer before removing old ones manually. Catalog requests retain at most 20 games and 512 KiB of
JSON, adapting down to five or one game when metadata is large. Individual oversized metadata and histories above
512 rows/512 KiB stop with a bounded-memory error. Downloads support at most 64 MiB compressed / 32 MiB extracted.

## Validation limits

Desktop integration tests exercise real HTTP with a synthetic RomM fixture, recovery, guarded writes, conflicts,
expired/rotating sessions, tied save timestamps and ambiguous upload responses. A real RomM 5.4.0 instance is also
used with a uniquely named temporary slot and synthetic bytes; its pre-existing saves are checked unchanged and
test rows/device are removed afterward. This does not establish real-game save correctness on hardware.

Physical New 3DS Wi-Fi, SD power-loss behavior, FBI installation, controls and real SRAM/FLASH/EEPROM gameplay round
trips still require the hardware acceptance plan. Do not treat emulator or desktop results as those hardware tests.
